# Prompt 实验记录：同一问题三种问法（Week 2 任务）

> 实验脚本：`python -m src.phase0.prompt_lab`（完整回答自动存 `notebooks/results/`）
> 判分基准：AP-21《航空器型号合格审定程序》MC 定义表（正确映射见 `domain_notes.md` 第四节）：
> MC0 符合性声明 / MC1 说明性文件 / MC2 分析计算 / MC3 安全评估 / MC4 实验室试验 /
> MC5 地面试验 / MC6 飞行试验 / MC7 航空器检查 / MC8 模拟器试验 / MC9 设备鉴定

## 实验设置

- 固定变量：模型 deepseek-v4-flash、温度 0.7、思考模式关、无 system prompt
- 唯一变量：问法
- 共 9 次调用：首轮 `prompt_lab_20260816_1929.md`（各 1 次）+ 复跑 `prompt_lab_20260816_1933.md`（各 2 次）

| 组 | 问法 | 假设 |
|----|------|------|
| A 直白 | "什么是 MC0-MC9？" | 假设：泛泛而谈，教科书口吻 |
| B 角色+背景 | 助理工程师 + 向主任汇报的处境 | 假设：更贴合使用场景，深度和实用性更好 |
| C 结构化 | 明确三步输出结构 | 假设：结构最好、信息密度最高，但可能限制发挥 |

## 观察记录

### A vs B：给上下文有多大差别？

- 准确性：差距是"错领域"与"对领域"的差距。A 三次调用撞出三个完全不同的错误领域——Minecraft 设备指纹、医学概念编码、LLM 思维链阶段，且每次语气笃定（"99% 的情况是指……"）。"MC"本身是多义缩写，无上下文时模型只能按概率猜，猜错时毫无愧色。B 域判断全对，始终锁定适航审定场景。
- 深度/广度：A 的"深度"是假深度——细节越丰富，错得越远。B 给出了真实的工程视角（证据强度 vs 成本周期的权衡、汇报话术），这部分知识可靠。
- 可用性（能直接用于汇报吗）：A 不可用。B 看起来最可用——**但恰恰是它最危险**（见下一节）。
- 长度对比：A 最长（在错误对象上铺陈）；B 次之；C 最紧凑。

### B vs C：自由发挥 vs 规定结构？——本实验最重要的发现

对照 AP-21 正确表逐条判分：

- **B（两轮三次）**：MC0-MC2 全对；MC3 之后几乎全错，且两次错法不同
  - 第 1 轮：MC3=地面试验、MC4=飞行试验、MC5=模拟器、MC6=检查、MC7=设备合格、MC8=航空器检查、MC9=持续适航文件
  - 第 2 轮：MC3=安全评估（对）、MC4=地面试验、MC5=试飞、MC6=模拟器、MC7=检查、MC8=设备合格、MC9="相似性/派生验证"（纯属编造，AP-21 无此项）
- **C**：首轮 MC0-MC6 全对、MC9 对（8/10），但 MC7/MC8 互换；复跑后 MC7-MC9 又换成另一种错法（MC8=设计评审/检查）

结构清晰度：C 的表格最好，可直接用作文档骨架；B 的叙事结构适合口头汇报。
遗漏了什么 / 多了什么：C 老实按指令分组，无多余发挥；B 自由发挥出了"汇报话术模板"这类超出问题的增值内容——但增值与编造混在一起，难以分辨。
哪种更适合"符合性方法选择思路"这类问题：**C 出骨架 + 人工核对事实**；B 的框架仅作参考。

### 温度的随机性（--repeat 2 实测）

- 同一问法、同温 0.7，事实性内容每次都不同：A 换了三个错域；B 的 MC 表两次错法不同；C 的 MC7-9 也不稳定。
- 温度 0.7 下**行文风格稳定，事实枚举不稳定**——随机性集中爆发在模型"没把握却必须给出确定答案"的地方。
- 工程含义：事实型任务要靠低温度 + 检索锚定，温度救不了知识问题。

## 结论

（第 1-4 条来自 chat_cli 会话实验，第 5 条来自本 prompt 实验）

1. **温度 = 随机度，不是"创造力旋钮"**：0.3 时回答专业稳定，1.5 时直接乱码。工程结论：对话任务用 0~0.7；后面项目里的 RAG 问答、工具调用都会用低温度，追求可复现。

2. **模型没有记忆，"多轮对话"是客户端的把戏**：API 每次都是无状态的。所谓记得上文，是因为程序把 messages 列表（`/history` 看到的那个）每次完整重发。`/new` 清空列表，模型立刻"失忆"——它自己都承认了。

3. **模型对条款细节不可信，而且越像真的越危险**：它两次把撤离演示说成 MC8（应为 MC5），思考模式里又亲口承认"表格我不确定，别编"。格式专业 ≠ 内容正确——这是整个项目的立项依据。

4. **问法决定回答质量**：直白问 → 泛泛而谈甚至错域；给角色和背景 → 贴合场景；规定输出结构 → 信息密度最高。chat_cli 的 system prompt 用的就是 B+C 组合。

5. **【本实验核心发现】角色/背景（B）和结构化（C）能把回答锁定到正确领域并组织得专业，但都无法保证枚举事实正确**——三种问法九次调用，MC0-MC9 对照表没有一次全对，B 甚至"越像能直接用的汇报材料越危险"。事实性内容必须外部锚定（查表/检索），prompt 只能改善表达、不能提供知识。

## 对项目后续的启示

- chat_cli 的 system prompt（适航工程顾问）借鉴了 B（角色+背景）+ C（先结论后展开、条款引用格式）的组合——它回答 TC/STC 时框架正确，但条款细节仍出错（撤离演示说成 MC8），与 B 的失败模式一致，印证"角色设定管不住事实"。
- 第 1 阶段 RAG 的回答 prompt 应硬性规定三件事：只依据检索到的条款原文回答；强制标注条款号（格式如 CCAR-25.813(b)）；检索不到相关条款时明确拒答——用"出处可核对"替代"语气可信"。
- 第 2 阶段 MC0-MC9 必须做成数据库方法定义库，moc_suggest 先查表、再交给 LLM 解释——LLM 不背枚举表。本实验的三张错表就是"让 LLM 背表"的后果预演。
